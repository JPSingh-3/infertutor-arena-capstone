1. Abstract and key findings

Several settings in the original harness never reached vLLM, so ablations run with it compared identical servers. Before tuning anything, this work fixed the harness, added in-container collection of vLLM's Prometheus metrics, and re-measured the four reference baselines plus a smoke test. Every number below has a client-side view and an engine-side view for the same time window, so each result can be explained rather than guessed at.

  1. Throughput is set by concurrency ÷ token gap. For every run, (requests running in vLLM) ÷ (vLLM's inter-token latency) predicts measured output tok/s within 2%. Faster tokens or more concurrent requests are the only two levers.
  2. Execution mode is the biggest engine effect seen so far, but it is not yet isolated. Compiled text runs step in 5.1–5.3 ms; eager mixed runs in 18–32 ms. Eager steps never drop below ≈18 ms even with 5 requests running, which points at CPU launch overhead. Mixed runs also carry prefill work in their steps, so the clean comparison (mixed traffic, eager vs compiled) is still to run.
  3. 4 GPUs did worse than 2 on mixed traffic (2,635 vs 2,713 tok/s; TTFT p95 2,655 vs 1,125 ms). Replicas completed 693 vs 164 requests in the same window, with the same average request size, so the imbalance is in how many requests each replica received. Hypothesis, not yet proven: Modal's 64-input limit lets it route to a replica whose vLLM batch (32) is already full.
  4. Much of the client's wait is not covered by vLLM's timers. On text runs, client TTFT was 0.8–1.6 s while vLLM reported 24–37 ms, and 40–57 requests per replica were in flight but not yet running or queued in the engine. The gap grows with streamed chunks per replica. It could be the network, the Modal proxy, the vLLM API server, or streaming buffers; per-hop timestamps are needed to split it.
  5. The text benchmark is 87% prefix-cache hits because 10 fixed questions repeat. Mixed traffic is 6%. Text results flatter the engine.
  6. Tuning results (section 8): the default execution mode (torch.compile + CUDA graphs, not yet separated) gives 2× (mixed) to 2.8× (text) the throughput of --enforce-eager on one GPU; max-num-seqs 128 adds another 35%; capping Modal at 32 inputs per replica coincided with balanced replicas (2 runs; cause not proven); raising Modal's limit gave text +42% (5,667 tok/s per H100); the cache, chunking and image flags, a bigger token budget, FP8 and vLLM 0.33 changed little; CPU reservation did not matter.
  7. Cost: $0.24 per 1M output tokens (text, 4 GPUs, compiled) up to $1.67 (mixed, 4 GPUs, eager). The worst run is 7× more expensive per token, mostly from load imbalance and eager mode.

2. System architecture

A load tester on a laptop sends streaming OpenAI-style chat requests over the internet to a Modal web endpoint. Modal routes each request to one of N identical containers. Each container runs a vLLM OpenAI server on one H100, plus a sampler thread that reads vLLM's /metrics every 2 s and appends them to a Modal Volume. After the run, the runner downloads those files and joins them to the client results by timestamp.

Orange borders: places where time is spent that the engine's metrics cannot see. Sections 6 and 7 show this is where most of the client's TTFT goes.

Analysis: replica C is pinned at 32 running with 5–28 more queued for the whole window, while replica B never has more than 9. Requests that land on C wait in its queue even though B is nearly idle. Engine queue time tripled (200 → 585 ms) and drives the TTFT tail.

Replica B's sampler has gaps, so its window is 49 s; req/s uses each replica's own span. Step time = window ÷ engine iterations. The replicas sum to 1,845 finished requests against the client's 1,824: the client counts requests that started after ramp-up, while vLLM's counter counts every request that finished between the samples around the window, including some ramp-up requests. A 1% gap is expected from that.

Request sizes are similar on every replica, so B was simply sent about a third as many requests as C. C never held more than 59 requests (32 running + 27 waiting), just under Modal's 64-input limit. Hypothesis: Modal's router treats a replica as available until it holds 64 inputs, while vLLM only runs 32, so it keeps sending work to a replica whose batch is full. This fits the data but does not prove why the router chose C over B. The test is to run E4 with concurrent_inputs 32 and 16 and compare requests per replica.

A second factor: E4 had only 20% more users than E3 for twice the GPUs. In a closed loop, throughput is capped at users ÷ (latency + pause) = 120 ÷ (3.3 + 0.7) s ≈ 30 req/s. Even with perfect balance, E4 could not have doubled E3's throughput at 120 users.

7.1 Throughput is concurrency divided by token gap

If each running request gets one token per engine step, output tok/s ≈ (requests running across replicas) ÷ (engine ITL). This simple model, using only vLLM's own gauges, predicts every run within 2%.

So there are two ways to get more throughput: keep more requests running (more users, a higher --max-num-seqs, better balancing) or make each step faster (compiled mode, FP8, a smaller step).

7.2 Engine step time: compiled vs eager against the bandwidth floor

Each dot is one run: mean requests running per replica against the engine's mean ITL. The dashed line is the memory-bandwidth floor from section 3.

CompiledEagerBandwidth floor ≈ 2.8 ms

Compiled text steps sit at 5.1–5.3 ms, about 1.9× the floor. Eager steps never go below ≈18 ms: E4's replica B took 18.5 ms per step with only 53 tokens per step, and the E0 smoke test 19 ms with 6 requests running. A floor that doesn't move with load points to fixed per-step overhead such as CPU kernel launches. Above that floor, steps grow with prefill work: replica C took 32 ms at 336 tokens per step. So the 22–26 ms eager ITL on mixed traffic is roughly 18 ms of overhead plus prefill interference.

Caveat: every compiled point here is text-only and every eager point is mixed. Section 8.2 later runs mixed traffic in both modes and confirms execution mode as the main factor.

7.4 Requests not yet seen by the engine

Little's law gives requests in flight per replica = request rate × latency ÷ replicas. Subtracting what vLLM reports as running or waiting leaves the requests held before the engine.

Inside vLLM engineBefore the engine
Show as table

The count of requests not yet in the engine follows the streamed chunk rate per replica: 2 at 650 chunks/s, 6 at 1,350, 40–57 at 3,350–4,600. A fixed network delay would not grow like that, but this does not locate the delay. The gap between client and engine can include:

  • client-side scheduling and connection setup,
  • the internet path and the Modal proxy, including Modal's own per-replica queue,
  • vLLM's API server: HTTP parsing, chat template, tokenization, image preprocessing, and the handoff to the engine,
  • streaming back: SSE writes, proxy and client buffering.

vLLM's TTFT timer covers only part of that path, and its exact start point in 0.21 still needs to be checked in the source. The fix is to measure each hop: client send time, container ingress (a small ASGI middleware in front of vLLM), vLLM arrival, and first token written. Running the load tester in Modal's region then removes the internet leg.

  • E4 imbalance on the chart: its four dots spread from 50 to 213 FLOP/byte because each replica got a different amount of work. Replicas C and D also took ≈ 30 ms per step against ≈ 19 ms on A and B, even though D had less work than A. Extra step time that doesn't follow the work suggests host-level differences between containers, such as a slower CPU, which matter most in eager mode. The harness should record each container's CPU model.

How these points are estimated (not profiler measurements). Per replica, over the measured window, from vLLM counters: engine steps, generated tokens, prompt tokens actually computed (prefix-cache hits excluded), images processed, and mean prompt length.

FLOPs = 2 × 3.63 B language-model parameters × tokens computed + LM head on generated tokens + attention (4 × 36 layers × 4,096 × context per token) + vision encoder (≈ 0.42 B parameters × 1,496 patches per image). Bytes = all LM weights read once per step (8.0 GB) + KV cache read for each generated token (144 KiB × context) + KV written + vision weights on steps with images. Activations and CPU work are ignored.

vLLM 0.21 has estimated_flops_per_gpu and estimated_read_bytes_per_gpu counters, but they read zero in these runs. To validate the estimates, the next runs should enable those counters or record DRAM throughput with DCGM (DRAM_ACTIVE).

8. Optimization experiments (steps 2–7)

One change at a time on 1 H100 (except step 3), same seed, vLLM 0.21 unless noted. Every run had 0 errors. Most are single runs, so differences under ≈ 10% should be treated as noise.

  • This answers the confound from section 7.2: on the same mixed traffic, eager vs compiled is a 2× difference. Text gains more because its steps carry almost no prefill.
  • Knee points: eager saturates at ≈ 50 users, compiled at ≈ 80 (both traffic types). Past the knee, throughput is flat and only TTFT grows.
  • At the knee, mixed compiled is limited by max-num-seqs: 31.5 of 32 running with up to 28 waiting. Text compiled is not: only ≈ 25 running, nothing waiting, yet TTFT grows from 0.3 to 2.6 s, all of it before the container's HTTP server. At ≈ 42 req/s, Modal's 64-input limit per container is the likely cap; this needs a concurrent_inputs test on text.
  • Compile and CUDA-graph capture added only ≈ 2–4 s to startup with the persistent cache; cold start was 128–190 s either way.

9. Limitations

  • Closed-loop load only. Users wait for a reply before sending again, so at 150 users several configs hit the same ≈ 3,700 tok/s ceiling. An open-loop rate sweep (e.g. vllm bench serve --request-rate) is needed to find true engine capacity.
  • One run per config. Run-to-run noise on this setup has not been measured, so single runs can't detect effects below roughly 20–30%. Each config should be repeated 3 times.
  • Eager vs compiled is confounded with traffic type. Text runs were compiled and mixed runs eager, so text-vs-mixed comparisons change two things at once.
  • Users were not scaled with GPUs. E4 has 2× E3's GPUs but only 1.2× its users.
  • The load tester ran on a laptop over the internet. Client TTFT and ITL include that path. The client was not overloaded (event-loop lag p99 ≤ 11 ms, CPU ≤ 25%).
  • Short windows. 50–65 s of steady state; the histogram percentiles from vLLM are bucket bounds, not exact values.
  • Unverified timer boundaries. Where vLLM 0.21 starts its TTFT timer has not been checked in the source, so "outside the engine" means "outside vLLM's timers".
  • Quality not measured. The official score multiplies by a quality pass rate that only the instructor's evaluator computes.
